## 1. Netzwerk-Setup

Zuerst wurde das bestehende `uglifiedserver_default`-Netzwerk entfernt, da es den Subnet `172.18.0.0/16` bereits belegte:

```powershell
docker network rm uglifiedserver_default
docker network create --subnet=172.18.0.0/16 tbz
```

## 2. Container erstellen

Vier busybox-Container wurden erstellt:
- **busybox1** und **busybox2** → default bridge Netzwerk
- **busybox3** und **busybox4** → user-defined Netzwerk `tbz`

```powershell
docker run -dit --name busybox1 busybox
docker run -dit --name busybox2 busybox
docker run -dit --name busybox3 --network tbz busybox
```

|-------------------------|---------------|
| `ping -c 3 busybox2`    | ❌ Fehler (bad address) – kein DNS im default bridge |

## 7. Gemeinsamkeiten und Unterschiede

### Gemeinsamkeiten
- Beide Netzwerke sind vom Typ `bridge`
- Container im gleichen Netzwerk können sich gegenseitig per **IP-Adresse** erreichen
- Beide haben einen eigenen Default-Gateway

### Unterschiede

| Eigenschaft         | default bridge         | user-defined (tbz)       |
|---------------------|------------------------|--------------------------|
| DNS / Namensauflösung | ❌ Nicht vorhanden    | ✅ Automatisch vorhanden |
| Ping per Name       | ❌ Funktioniert nicht  | ✅ Funktioniert          |
| Ping per IP         | ✅ Funktioniert        | ✅ Funktioniert          |
| Netzwerkisolation   | Getrennt von tbz       | Getrennt von bridge      |
| Subnet              | 172.17.0.0/16          | 172.18.0.0/16            |
| Gateway             | 172.17.0.1             | 172.18.0.1               |

### Schlussfolgerung
Container in **verschiedenen Netzwerken** können sich nicht erreichen – Docker isoliert die Netzwerke voneinander. Im **default bridge** Netzwerk gibt es keine automatische DNS-Auflösung, weshalb ein Ping per Containername nicht funktioniert. Im **user-defined Netzwerk** (`tbz`) stellt Docker automatisch DNS zur Verfügung, sodass Container sich gegenseitig beim Namen kennen und erreichen können. Für produktive Setups sind user-defined Netzwerke deshalb klar zu bevorzugen.

## 8. Fragen zu KN02

### In welchem Netzwerk befanden sich der Web- und der DB-Container?
Beide Container befanden sich im **default bridge** Netzwerk, da kein eigenes Netzwerk angegeben wurde.

### Weshalb funktionierte die Verbindung über die IP-Adresse des DB-Containers?
Weil beide Container im gleichen Netzwerk (default bridge) waren, konnten sie sich über IP-Adressen direkt erreichen. Docker erlaubt die Kommunikation zwischen Containern im gleichen Netzwerk über deren IP.

### Weshalb ist diese Lösung mit einer direkt eingetragenen Container-IP nicht ideal?
Container-IP-Adressen sind **dynamisch** – sie können sich bei jedem Neustart des Containers ändern. Wenn die IP des DB-Containers wechselt, muss die Konfiguration des Web-Containers manuell angepasst werden, was fehleranfällig und nicht wartbar ist.

### Verbesserungsvorschlag
Ein **user-defined Netzwerk** erstellen und beide Container darin betreiben. Dadurch steht automatisch DNS zur Verfügung und der Web-Container kann den DB-Container über seinen **Containernamen** (z.B. `db`) ansprechen – unabhängig von der IP-Adresse.

## 9. Verbesserungsvorschlag & Umsetzung

### Netzwerk erstellen

```powershell
docker network create kn02-netz
```

### Alte Container stoppen und entfernen

```powershell
docker stop web db
docker rm web db
```

### Container neu starten im gemeinsamen Netzwerk

```powershell
docker run -d --name db --network kn02-netz `
  -e MYSQL_ROOT_PASSWORD=meinPasswort `
  -e MYSQL_DATABASE=meineDatenbank `
  mysql:8.0

docker run -d --name web --network kn02-netz `
  -e DB_HOST=db `
  -p 8080:80 `
  mein-web-image
```

> Der entscheidende Unterschied: `DB_HOST=db` verwendet den **Containernamen** statt einer IP-Adresse. Dank DNS im user-defined Netzwerk wird `db` automatisch zur richtigen IP aufgelöst.

### Test

```powershell
# Webseite aufrufen
curl http://localhost:8080

# Oder im Browser: http://localhost:8080
```

📸 *Screenshot: Webseite lädt erfolgreich und greift auf DB zu*

### Resultat
Die Webseite kann weiterhin auf die Datenbank zugreifen – nun aber über den stabilen Containernamen `db` statt über eine dynamische IP-Adresse. Die Lösung ist robuster, wartbarer und entspricht den Best Practices für Docker-Netzwerke.
